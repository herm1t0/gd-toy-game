# One fixed 60 Hz tick; commands and events cross the seam

A **Match** advances in a single fixed 60 Hz simulation step, driven by one runner node from `_PhysicsProcess` with `dt = 1/60` taken from a constant and never from the frame delta. The 0.25 s engagement tick is every 15th step; income steps, **Build time** and sudden death are tick counts. Nothing in the game uses Godot `Timer` nodes, per-unit timers or `await`. Every mutation is a `Command` (`Recruit`, `StartUpgrade`, `StartResearch`, `Concede`) drained at the start of a step and validated by the sim, and both players implement one controller interface that reads a read-only snapshot and returns commands; the view layer reads that same snapshot plus a per-step event list (`Spawned`, `ShotFired`, `DamageLanded`, `Died`, `BuildCompleted`, `MatchEnded`, …).

One clock because ordering is the thing that goes wrong: whether a **Fight slot** frees before or after this step's attacks is a rule, and it should not depend on which timer fired first. One clock also makes the whole match reproducible in a test — a second, slower logic tick would have to re-derive movement intent at 10 Hz, which at 3 m/s march speed is a 0.3 m jump per update and visibly steppy. Commands rather than direct calls because the sim then owns every rule check (gold, **Build slot**, level III, **Army cap**), and because the map's "one player-controller seam with human and AI implementations" is otherwise a convention that the first convenient `sim.KillUnit()` call breaks.

**Considered options:** a 10 Hz logic tick decoupled from 60 Hz physics (cheaper to reason about, but movement intent stutters and there are two orderings to keep straight); per-system Godot `Timer`s and signals (idiomatic Godot, but ordering becomes implicit and untestable and the shared engagement tick stops being a property of the codebase); direct method calls into the sim from UI and AI (fewer layers, but the AI could reach past the rules and the seam survives only as a comment); views diffing consecutive snapshots instead of consuming events (a hit that flashed and passed is simply absent from a snapshot, so every hit flash, health bar reveal and splash ring becomes a bespoke diff heuristic).

**Consequences:** a pause stops stepping the sim while the scene tree keeps running, so camera, UI, animation and audio stay live — `SceneTree.Paused` would freeze the UI with it. Game speed is an **integer** step multiplier (1× / 2× / 4×) rather than a scaled `dt`, so speed changes wall-clock only and never outcomes, which keeps #15's "10 minutes at 1×" a testable claim; 4× is 240 sim steps per second over ≤30 units. The event list is drained and cleared every step, so it never grows. The AI's decision cadence is #13's policy sitting on top of this seam — it sees the snapshot and nothing else. A scripted two-sided match is the natural way to test the runner, and the view layer stays manually smoke-tested because there is no GdUnit4 build for 4.8.
